## What resource kinds exist beyond collection+document (singleton, contained, media/stream, derived/polymorphic, view/aggregate, event/feed, "me"/current-user alias, preview/dry-run)?

### Takeaway

The standards collectively define about fifteen distinct resource shapes; the catalog covers collection/document, singleton, store, association, job and owned child, but has no shape for media/stream resources, side-effect-free function resources, unbound (resource-less) operations, aggregate/view resources, event/change-feed resources, principal-alias ("me") resources, write-only ingest endpoints, operation/status-monitor resources, job executions, or staged "experiment/preview" resources. Polymorphic (derived) types, open/extensible types and keyless complex types are type-system kinds rather than endpoint shapes and are also absent.

### Cited Findings

**Baseline: collection + document**

- AIP-121: "The methods can be either the standard methods (Get, List, Create, Update, Delete), or custom methods."; "A resource must support at minimum Get"; "A resource must also support List, except for singleton resources where more than one resource is not possible." — [AIP-121](https://google.aip.dev/121)
- AIP-121 also requires that relationships form a DAG ("must be representable via a directed acyclic graph") and that standard methods are strongly consistent ("a get request for a resource must return the resource") — [AIP-121](https://google.aip.dev/121)
- OData: "Entity types are nominal structured types with a key that consists of one or more references to structural properties."; "An entity set MUST contain only instances of its specified entity type or its subtypes." — [OData CSDL XML 4.01](https://docs.oasis-open.org/odata/odata-csdl-xml/v4.01/odata-csdl-xml-v4.01.html)
- Massé's four archetypes, as reproduced by secondary sources: document = "a singular concept that is akin to an object instance or database record"; collection = "a server-managed directory of resources"; store = "a client-managed resource repository"; controller = "a controller resource models a procedural concept" — [restfulapi.net](https://restfulapi.net/resource-naming), [NBB REST API Design Guide wiki](https://github.com/NationalBankBelgium/REST-API-Design-Guide/wiki/REST-Resources-Single-items-and-collections)
- Massé's naming/method rules, per a summary of the book: document URIs singular noun; collection and store URIs plural noun; controller = "Verb or verb phrase", e.g. `POST /alerts/245743/resend`; "PUT must be used to insert and update the stored resources"; "Must use POST to create a new resource in a collection"; "POST must be used to execute the controller"; "CRUD function names should not be used in URIs" — [javenjin summary of the Rulebook](https://javenjin.github.io/blog/p/rest-api-design-rulebook)

**Singleton**

- AIP-156: "A singleton resource must always exist by virtue of the existence of its parent, with one and exactly one per parent."; "Singleton resources must not define the Create or Delete standard methods."; "Singleton resources should define the Get and Update methods."; must not define Update "if all fields on the resource are output only". Pattern `users/{user}/config`; `GET /v1/{name=users/*/config}`; optional List `GET /v1/{parent=users/*}/configs` implemented per AIP-159 ("To list all configs, use `-` as the user id.") — [AIP-156](https://google.aip.dev/156)
- OData singleton is a *top-level named* entity (not parent-scoped): "A singleton MUST reference an instance its entity type."; addressed as `http://host/service/BestProductEverCreated` — [OData CSDL XML 4.01 §13.3](https://docs.oasis-open.org/odata/odata-csdl-xml/v4.01/odata-csdl-xml-v4.01.html), [OData URL Conventions 4.01 §4.3](https://docs.oasis-open.org/odata/odata/v4.01/odata-v4.01-part2-url-conventions.html)
- Geewax ch. 12 "Singleton sub-resources" outline: 12.3.1 Standard methods, **12.3.2 Resetting**, 12.3.3 Hierarchy, 12.4.1 Atomicity, 12.4.2 Exactly one sub-resource; chapter bullets: "Why and when we should split data off into a singleton sub-resource", "How standard methods interact with sub-resources" — [Manning livebook ch. 12](https://livebook.manning.com/book/api-design-patterns/chapter-12)

**Store (client-keyed, upsert)**

- Massé store: client-managed repository, PUT to insert and update (see above).
- AIP-133: "A `{resource}_id` field must be included for management plane resources"; it "must exist on the request message, not the resource itself"; duplicate ID → `ALREADY_EXISTS` — [AIP-133](https://google.aip.dev/133)
- AIP-134: "If the service uses client-assigned resource names, Update methods may expose a bool allow_missing field"; then "the resource is created. All fields are applied regardless of any provided field mask." — [AIP-134](https://google.aip.dev/134)
- OData Upsert (§11.4.4): "the service MUST handle the request as a create entity request or fail the request altogether"; "The service MUST NOT treat an update request containing an If-Match header as an insert."; "A PUT or PATCH request MUST NOT be treated as an update if an If-None-Match header is specified with a value of *."; "Upserts are not supported against media entities" — [OData Protocol 4.01](https://docs.oasis-open.org/odata/odata/v4.01/odata-v4.01-part1-protocol.html)
- Azure: "DO use PUT with JSON for wholesale create/replace operations."; "YOU SHOULD use PUT or PATCH to create a resource"; rules table: resource missing → create → `201-Created`; exists → PATCH update / PUT overwrite → `200-OK` — [Azure REST API Guidelines](https://github.com/microsoft/api-guidelines/blob/vNext/azure/Guidelines.md)
- Graph "Upsert" pattern: idempotent create-or-update with a client-provided key; "SHOULD additionally use PATCH to create new entities" with the key in the URL — [Graph guidelines](https://github.com/microsoft/api-guidelines/blob/vNext/graph/GuidelinesGraph.md)
- Zalando [148]: "PUT requests are usually robust against non-existence of resources by implicitly creating the resource before updating."; POST: "The resource identifier MUST NOT be passed as request body data by the client" — [Zalando guidelines](https://opensource.zalando.com/restful-api-guidelines/#148)
- JSON:API: "A server MAY accept a client-generated ID along with a request to create a resource."; the id "MUST be a universally unique identifier"; unsupported → `403 Forbidden` — [JSON:API 1.1](https://jsonapi.org/format/)

**Contained / owned child vs. independent nested child**

- OData containment: "A navigation property MAY indicate that instances of its declaring structured type contain the targets"; canonical URL of a contained entity "is the canonical URL of the containing entity followed by:" the navigation path — [CSDL XML 4.01](https://docs.oasis-open.org/odata/odata-csdl-xml/v4.01/odata-csdl-xml-v4.01.html), [URL Conventions 4.01 §4.3.2](https://docs.oasis-open.org/odata/odata/v4.01/odata-v4.01-part2-url-conventions.html)
- OData referential constraint / OnDelete: "A single-valued navigation property MAY define one or more referential constraints."; on-delete values "Cascade, meaning the related entities will be deleted if the source entity is deleted", "None, meaning a DELETE request on a source entity with related entities will fail", SetNull, SetDefault — [CSDL XML 4.01](https://docs.oasis-open.org/odata/odata-csdl-xml/v4.01/odata-csdl-xml-v4.01.html)
- AIP-124: "A resource must have at most one canonical parent" — [AIP-124](https://google.aip.dev/124)
- AIP-135 cascading delete: "The API must fail with a FAILED_PRECONDITION error if the force field is false (or unset) and child resources are present." — [AIP-135](https://google.aip.dev/135)
- Zalando: [143] "MUST identify resources and sub-resources via path segments" (`/resources/{id}/sub-resources/{id}`); [145] nest only when a sub-resource cannot exist without its parent; [147] at most about three sub-resource levels; [146] limit resource types (≈4–8) — [Zalando guidelines](https://opensource.zalando.com/restful-api-guidelines/#143)
- AIP-123 allows several name patterns for one resource type (multi-parent): "When multiple patterns are defined within a resource, these patterns must be mutually unique" — [AIP-123](https://google.aip.dev/123)

**Keyless embedded structure (complex type)**

- OData: "Complex types are keyless nominal structured types." — [CSDL XML 4.01](https://docs.oasis-open.org/odata/odata-csdl-xml/v4.01/odata-csdl-xml-v4.01.html)
- Graph: "you SHOULD use entity types to model addressable resources"; "Complex types are better suited to represent composite properties of API entities."; "an entity type declares a key property to uniquely identify its objects, and a complex type doesn't" — [Graph guidelines](https://github.com/microsoft/api-guidelines/blob/vNext/graph/GuidelinesGraph.md)

**Media / stream resources**

- OData: "Media entities are entities that represent a media stream, such as a photo."; "Edm.Stream is a primitive type that can be used as a property of an entity type or complex type" — [CSDL XML 4.01](https://docs.oasis-open.org/odata/odata-csdl-xml/v4.01/odata-csdl-xml-v4.01.html)
- OData HTTP surface: "A POST request to a media entity's entity set creates a new media entity." (§11.4.7.1); "A successful PUT request to the media edit URL of a media entity changes the media stream of the entity." (§11.4.7.2); "Deleting a media entity also deletes the media associated with the entity." (§11.4.7.3); stream property: "A successful PUT request to the edit URL of a stream property changes the media stream associated with that property." (§11.4.8.1), DELETE sets it to null (§11.4.8.2); read via `GET .../Pictures('Sunset4321299432')/$value` — [OData Protocol 4.01](https://docs.oasis-open.org/odata/odata/v4.01/odata-v4.01-part1-protocol.html), [URL Conventions 4.01 §4.14](https://docs.oasis-open.org/odata/odata/v4.01/odata-v4.01-part2-url-conventions.html)
- Stripe File: "This object represents files hosted on Stripe's servers."; endpoints `POST /v1/files`, `GET /v1/files/:id`, `GET /v1/files`; upload is "a `multipart/form-data` request to https://files.stripe.com/v1/files" with a `purpose` and a `file`; content at `GET /v1/files/{id}/contents`; anonymous download through a separate `file_link` resource (`POST /v1/file_links`) — [Stripe Files](https://docs.stripe.com/api/files), [Stripe file upload guide](https://docs.stripe.com/file-upload)
- Azure "Bring Your Own Storage": "DO use the Bring Your Own Storage pattern." (service reads/writes blobs in customer storage rather than taking bytes in the API) — [Azure guidelines](https://github.com/microsoft/api-guidelines/blob/vNext/azure/Guidelines.md)

**Derived / abstract / polymorphic types**

- OData: "An entity type MAY indicate that it is abstract and cannot have instances."; "An entity type can inherit from another entity type by specifying it as its base type."; type-cast path segment `http://host/service/Customers/Model.VipCustomer` (§4.11) — [CSDL XML 4.01](https://docs.oasis-open.org/odata/odata-csdl-xml/v4.01/odata-csdl-xml-v4.01.html), [URL Conventions 4.01](https://docs.oasis-open.org/odata/odata/v4.01/odata-v4.01-part2-url-conventions.html)
- Azure: "DO define a discriminator field indicating the kind of the resource and include any kind-specific fields in the body."; "YOU SHOULD NOT allow an update (patch) to change the discriminator field of a polymorphic type."; "YOU SHOULD NOT have a property of an updatable resource whose value is an array of polymorphic objects." — [Azure guidelines](https://github.com/microsoft/api-guidelines/blob/vNext/azure/Guidelines.md)
- Graph offers three alternative models: **type hierarchy** (abstract base + subtypes; filters need cast segments), **facets** (one entity with common properties plus one nullable complex facet per variant), **flat bag** (one entity with all properties plus a type discriminator) — [Graph guidelines](https://github.com/microsoft/api-guidelines/blob/vNext/graph/GuidelinesGraph.md), [Graph patterns directory](https://github.com/microsoft/api-guidelines/tree/vNext/graph/patterns)
- Graph "collection subsets" pattern uses the same mechanism for all/none/enumerated membership: "Have an abstract base class where all variants of the subset are derived types from the base subset." with `"membershipKind": "all"` / `"enumerated"` + `members` — [Graph subsets pattern](https://github.com/microsoft/api-guidelines/blob/vNext/graph/patterns/subsets.md)
- Geewax ch. 16 is titled "Polymorphism" — [Manning book page](https://www.manning.com/books/api-design-patterns) (title only verified; see Gaps)

**Open / extensible types, metadata bags**

- OData: "An entity type MAY indicate that it is open and allows clients to add properties dynamically" — [CSDL XML 4.01](https://docs.oasis-open.org/odata/odata-csdl-xml/v4.01/odata-csdl-xml-v4.01.html)
- AIP-148 `annotations`: "To store small amounts of arbitrary data, a map<string, string> annotations field may be added." — [AIP-148](https://google.aip.dev/148)
- Stripe metadata: "You can specify up to 50 keys, with key names up to 40 characters long and values up to 500 characters long."; "Stripe doesn't use metadata" — [Stripe metadata](https://docs.stripe.com/api/metadata)
- Graph "Dictionary" pattern: let clients supply an open-ended set of same-type elements — [Graph guidelines](https://github.com/microsoft/api-guidelines/blob/vNext/graph/GuidelinesGraph.md)

**Function / controller / unbound operation resources**

- OData: "Functions are operations exposed by an OData service that MUST return data and MUST have no observable side effects." (GET; "If the function is composable, additional path segments may be appended to the URL"); "Actions are operations exposed by an OData service that MAY have side effects when invoked." and "MUST NOT be further composed with additional path segments" (POST) — [OData Protocol 4.01 §11.5](https://docs.oasis-open.org/odata/odata/v4.01/odata-v4.01-part1-protocol.html)
- OData bound vs unbound: "A bound action or function overload MUST specify at least one parameter; the first parameter is the binding parameter."; "Unbound actions are invoked through an action import."; examples `GET /service/Products/Model.MostExpensive()` (bound to collection), `GET /service/ProductsByCategoryId(categoryId=2)` (function import), `POST /service/Customers('ALFKI')/SampleEntities.CreateOrder` (bound action, supports `If-Match`) — [CSDL XML 4.01 §12](https://docs.oasis-open.org/odata/odata-csdl-xml/v4.01/odata-csdl-xml-v4.01.html), [OData Protocol 4.01](https://docs.oasis-open.org/odata/odata/v4.01/odata-v4.01-part1-protocol.html)
- AIP-136 stateless methods: "Some custom methods are not attached to resources at all."; "The URI should place both the verb and noun after the `:` separator" (example `:translateText`) — [AIP-136](https://google.aip.dev/136)
- AIP-130 "Stateless Methods": "a method that has no permanent effect on any data within the API (e.g. translating text)" — [AIP-130](https://google.aip.dev/130)

**View / aggregate / computed resources**

- AIP-130 names "Custom collection fetch methods: fetch information across a collection that cannot be expressed via a standard method" and "Custom resource fetch methods" — [AIP-130](https://google.aip.dev/130)
- OData `$count` segment: `GET /service/Products/$count` (§4.8); `$crossjoin`: `GET /service/$crossjoin(Products,Sales)?$filter=Products/ID eq Sales/ProductID` (§4.15); `$all`: "identifies the collection of all entities in a service" (§4.16) — [URL Conventions 4.01](https://docs.oasis-open.org/odata/odata/v4.01/odata-v4.01-part2-url-conventions.html)
- OData Data Aggregation: "A transformation sequence may be invoked using the system query option `$apply`."; "The `groupby` transformation partitions the input set by the values of certain "grouping properties""; examples `GET /service/Sales?$apply=aggregate(Amount with sum as Total)`, `...?$apply=groupby((Product/Name),aggregate(Amount with sum as Total))/orderby(Total desc)`; "Services can define custom aggregation methods" — [OData Data Aggregation Ext v4.0](https://docs.oasis-open.org/odata/odata-data-aggregation-ext/v4.0/odata-data-aggregation-ext-v4.0.html)
- GitHub exposes derived read-only sub-resources, e.g. `GET /repos/{owner}/{repo}/pulls/{pull_number}/commits`, `.../files`, `GET /repos/{owner}/{repo}/stargazers` — [GitHub pulls](https://docs.github.com/en/rest/pulls/pulls), [GitHub starring](https://docs.github.com/en/rest/activity/starring)

**Event / feed resources**

- Stripe Event: "When the state of another API resource changes, Stripe creates an `Event` object that contains all the relevant information associated with that action, including the affected API resource."; endpoints only `GET /v1/events/:id` and `GET /v1/events`; "You can access events through the Retrieve Event API for 30 days." — [Stripe Events](https://docs.stripe.com/api/events)
- Stripe v2: "Events emitted from APIs in the `/v2` namespace are thin events"; v1 events mostly "include a snapshot of an API object in their payload"; event destinations are a resource (`/v2/core/event_destinations`) — [Stripe API v2 overview](https://docs.stripe.com/api-v2-overview)
- Zalando: [194] "MUST treat events as part of the service interface"; [201] "MUST use general events to signal steps in business processes"; [202] "MUST use data change events to signal mutations"; [242] "MUST provide explicit event ordering for data change events"; [205] "SHOULD ensure that data change events match the APIs resources"; [211] unique event identifiers; [247] mandatory event metadata — [Zalando guidelines](https://opensource.zalando.com/restful-api-guidelines/#194)
- OData/Graph delta feeds are covered under the change-feed key question below.

**"Me" / current-principal alias**

- GitHub: `GET /user` (authenticated user's profile), `PATCH /user`, versus `GET /users/{username}` for any user; principal-scoped collections `GET /user/starred`, `GET /user/issues`, mirrored by `GET /users/{username}/starred` — [GitHub users](https://docs.github.com/en/rest/users/users), [GitHub starring](https://docs.github.com/en/rest/activity/starring), [GitHub issues](https://docs.github.com/en/rest/issues/issues)

**Preview / dry-run / staged-change resources**

- Stripe: `POST /v1/invoices/create_preview` — "you are simply viewing a preview – the invoice has not yet been created. As such, the upcoming invoice will not show up in invoice listing calls, and you cannot use the API to pay or edit the invoice." The response is a normal `invoice` object with a synthetic id (`upcoming_in_...`). — [Stripe create preview invoice](https://docs.stripe.com/api/invoices/create_preview)
- AIP-236 Policy preview: "Preview is a rollout safety mechanism for policy resources"; "A new configuration of a policy to be previewed is stored as a nested collection under the policy."; "These nested collections are known as experiments."; experiment has standard methods plus `POST /v1/{name=policies/*/experiments/*}:startPreview`, `:stopPreview` and optional `:commit` ("to promote an experiment"); state toggles ACTIVE ↔ SUSPENDED — [AIP-236](https://google.aip.dev/236)
- AIP-163 `validate_only` (operation-level dry run) is listed under the operations key question.

**Operation / status-monitor resources and jobs**

- AIP-151: an LRO method "should return a google.longrunning.Operation object instead of the ultimate response message"; "APIs with messages that return Operation must implement the Operations service."; "Individual APIs must not define their own interfaces for long-running operations"; parallel operation not allowed → `ABORTED`; operations "may ... expire after sufficient time" (rule of thumb 30 days) — [AIP-151](https://google.aip.dev/151)
- OData async: `Prefer: respond-async` → `202 Accepted` + `Location` of a status monitor; "A GET request to the status monitor resource returns 200 OK once the asynchronous processing has completed."; "A DELETE request sent to the status monitor resource requests that the asynchronous processing be canceled." — [OData Protocol 4.01 §11.6](https://docs.oasis-open.org/odata/odata/v4.01/odata-v4.01-part1-protocol.html)
- Azure LRO: "DO include an `operation-location` response header with the absolute URL of the status monitor for the operation."; client may pass `Operation-Id`; status values "NotStarted", "Running", "Succeeded", "Failed", "Canceled"; "DO NOT use a long-running POST to create a resource -- use PUT"; "DO NOT implement PATCH as an LRO."; monitor retained "at least 24 hours" — [Azure guidelines](https://github.com/microsoft/api-guidelines/blob/vNext/azure/Guidelines.md)
- Graph LRO has two variants: **RELO** ("The returned resource is the targeted resource and includes the status of the operation.", 201 + `provisioning` status) and **stepwise operation** ("The returned resource is a new API resource called *stepwise operation*", 202 + `Location`) — [Graph LRO pattern](https://github.com/microsoft/api-guidelines/blob/vNext/graph/patterns/long-running-operations.md)
- AIP-152 Jobs: "An API may define a `Job` resource to represent a particular task with distinct setup, configuration, and execution"; resource name must end with "Job"; "The service should define all five of the standard methods"; "The service should define a `Run` custom method that executes the job immediately" (`POST ...:run`, returns an LRO); "The service may store resources representing individual executions along with their result" with Get, List, Delete on the execution resources — [AIP-152](https://google.aip.dev/152)
- JSON:API: accepted-but-unfinished create → "the server MUST return a 202 Accepted status code." — [JSON:API 1.1](https://jsonapi.org/format/)
- GitHub: the pulls page lists `PUT .../pulls/{pull_number}/merge-async` (202) with a result resource `GET .../merge-async/{uuid}`, and `PUT .../update-branch` returning 202 — [GitHub pulls](https://docs.github.com/en/rest/pulls/pulls) (as summarised by the fetch tool; I did not independently confirm the `merge-async` endpoints)

**Association resources and relationship-linkage resources**

- AIP-124: many-to-many "should use a repeated field containing a list of resource names" or "may model a many-to-many relationship using a sub-resource with two one-to-many associations" (e.g. `publishers/{publisher}/books/{book}/authors/{book_author}`), the latter when relationship metadata is needed — [AIP-124](https://google.aip.dev/124)
- JSON:API relationship endpoints: "A server MUST support fetching relationship data for every relationship URL provided as a self link" (`GET /articles/1/relationships/author`); to-many: PATCH replaces all members, POST "MUST add the specified members to the relationship unless they are already present", DELETE "MUST delete the specified members from the relationship or return a 403 Forbidden response" — [JSON:API 1.1](https://jsonapi.org/format/)
- OData `$ref`: "A successful POST request to a navigation property's references collection adds a relationship to an existing entity." (§11.4.6.1); DELETE on `.../$ref` removes (204); PUT on single-valued `$ref` changes; PUT with a collection of references replaces all (§11.4.6.4); address e.g. `Categories(1)/Products/$ref` — [OData Protocol 4.01](https://docs.oasis-open.org/odata/odata/v4.01/odata-v4.01-part1-protocol.html)
- GitHub membership-as-key: `PUT /user/starred/{owner}/{repo}` (204), `DELETE` (204), existence check `GET` → 204 if starred / 404 if not — [GitHub starring](https://docs.github.com/en/rest/activity/starring)
- AIP-122 cross reference fields: "the field should be of type string and accept the resource name of the other resource"; "The field should not be of type message using the message that implements the resource" — [AIP-122](https://google.aip.dev/122)
- Geewax ch. 13 "Cross references", ch. 14 "Association resources", ch. 15 "Add and remove custom methods" — titles per retailer listings: [Simon & Schuster listing](https://www.simonandschuster.com/books/API-Design-Patterns/JJ-Geewax/9781617295850)

**Reference data / enumerations (nearest thing to "Lookup")**

- AIP-126: "Enums should receive new values infrequently."; "For enums that change frequently, the API should use a string and document the format." — [AIP-126](https://google.aip.dev/126)
- Azure: "YOU SHOULD use extensible enumerations unless you are positive that the symbol set will NEVER change over time." — [Azure guidelines](https://github.com/microsoft/api-guidelines/blob/vNext/azure/Guidelines.md)
- Graph "Evolvable enums" pattern: adding a member after the sentinel is non-breaking — [Graph guidelines](https://github.com/microsoft/api-guidelines/blob/vNext/graph/GuidelinesGraph.md)

**Per-user view of a shared resource**

- Graph "Viewpoint": "A shared resource, such as a website or a group message, may have different states for different users"; modelled as a `viewpoint` complex property (e.g. `"viewpoint":{ "lastMessageReadDateTime": ... }`), updated by PATCH or an action such as `POST /chats/{id}/markChatReadForUser` — [Graph viewpoint pattern](https://github.com/microsoft/api-guidelines/blob/vNext/graph/patterns/viewpoint.md)

**Declarative-friendly resources**

- AIP-128: "Resources that are declarative-friendly must use only strongly-consistent standard methods for managing resource lifecycle"; should carry `bool reconciling` (output only; true "if the current state of the resource does not match the user's intended state"); "Resources must have an etag field"; "Resources should not employ custom methods"; "Resources should not implement soft-delete"; "Resources should provide change validation" — [AIP-128](https://google.aip.dev/128)

### Inferences

- None of the sources defines a "Lookup" (code+name reference data) resource kind. The nearest guidance is "use strings/extensible enums for frequently changing value sets" (AIP-126, Azure, Graph). Lookup is a Haldus-specific specialisation of Crud/ReadOnly, not a standards-derived archetype.
- "Singleton" means two different things: AIP-156/Geewax = exactly-one-per-parent, implicitly created, no Create/Delete, optionally listable across parents with `-`; OData = top-level named instance. If the catalog's Singleton is only the top-level form, the parent-scoped form (`users/{id}/config`, likely `Singleton` + `Under<Parent>`) and the Geewax "reset to defaults" operation are gaps.
- "Job" also means two things: AIP-151 Operation (a promise/status monitor that any method may return) and AIP-152 Job (a configured, re-runnable resource with `:run` and an executions sub-collection). The catalog's "Job (long-running operation)" reads like the former; the re-runnable Job + Execution shape looks missing or partial.
- OData containment maps to catalog `Detail`; AIP parent/child with independent lifecycle maps to `Under<Parent>`. The standards add options the catalog descriptions do not mention: on-delete behaviour (cascade / restrict / set-null), `force` cascading delete, multiple parent patterns for one type (AIP-123), and a nesting depth limit (Zalando [147]).
- Media/stream, function (safe custom fetch), unbound operation, aggregate/view, event feed, me-alias, preview and experiment have no counterpart in the catalog.
- Complex type (keyless owned value) is a building block rather than an endpoint shape; in EF Core terms it corresponds to owned/complex types. Worth an explicit decision because Graph explicitly asks designers to choose entity vs complex type.

## What operation kinds exist beyond the 5 standard methods (custom actions vs side-effect-free functions, upsert, batch, bulk by criteria, copy/move, add/remove on associations, search across collections, validate-only, undelete, expunge, rollback to revision)?

### Takeaway

AIP-130 gives the most complete method taxonomy (standard, batch, aggregated list, custom fetch, custom mutation incl. backup/restore/rename, stateless, streaming); OData adds the action/function split, deep insert/update, whole-collection update, `/$each` criteria updates/deletes and generic `$batch`. The catalog lacks: safe functions, criteria-based bulk update/delete, copy/move/rename, add/remove, validate-only, cross-collection reads and search, whole-collection replace, generic cross-resource atomic batch, and several sub-operations of soft delete and revisions (expunge, alias, rollback) that should be checked.

### Cited Findings

**AIP method taxonomy**

- AIP-130 categories: standard collection methods (List, Create); standard resource methods (Get, Update, Delete); "Batch resource methods: fetch or mutate multiple resources in a collection by name."; "Aggregated list methods: fetch or mutate multiple resources of the same type across multiple collections."; custom collection/resource fetch methods; custom mutation methods including "Backing up a resource: storing a copy of a resource at a particular point in time.", "Restoring a resource: setting a resource to a version from a particular point in time.", "Renaming a resource: modify the resource's name or id while preserving configuration and data."; "Stateless Methods"; "Streaming methods: methods that communicate via client, server, or bi-directional streams." — [AIP-130](https://google.aip.dev/130)
- AIP-131 Get: `GET`, no body, "The response must be the resource itself." — [AIP-131](https://google.aip.dev/131)
- AIP-132 List: `GET`; `page_size`, `page_token`, `next_page_token` mandatory; optional `order_by`, `filter`, `show_deleted` — [AIP-132](https://google.aip.dev/132)
- AIP-133 Create: `POST` on the collection with `parent`; LRO variant returns `google.longrunning.Operation` resolving to the resource — [AIP-133](https://google.aip.dev/133)
- AIP-134 Update: "The method should support partial resource update, and the HTTP verb should be PATCH."; PUT "is strongly discouraged"; "Update masks must support a special value *, meaning full replacement (the equivalent of PUT)."; "state fields must not be directly writable in update methods." — [AIP-134](https://google.aip.dev/134)

**Custom actions vs side-effect-free functions**

- AIP-136: "Custom methods should only be used for functionality that can not be easily expressed via standard methods"; "The HTTP URI must use a `:` character followed by the custom verb"; "The HTTP method must be `GET` or `POST`."; "`GET` must be used for methods retrieving data or resource state."; "`POST` must be used if the method has side effects or mutates resources or data."; resource-based (`name`), collection-based (`parent`, e.g. `:sort`), stateless (`:translateText`); examples `:archive` — [AIP-136](https://google.aip.dev/136)
- OData actions (POST, side effects, not composable) vs functions (GET, no side effects, composable); "Actions without a return type respond with" 204; available operations can be advertised per instance and "a function or action is not available for a particular instance by setting its value to null" — [OData Protocol 4.01 §11.5](https://docs.oasis-open.org/odata/odata/v4.01/odata-v4.01-part1-protocol.html)
- Azure: `https://.../<resource-collection>/<resource-id>:<action>?<input parameters>` and collection form `https://.../<resource-collection>:<action>`; "DO use a POST operation for any action on a resource or collection."; "DO NOT use an action operation when the operation behavior could reasonably be defined" as a standard operation — [Azure guidelines](https://github.com/microsoft/api-guidelines/blob/vNext/azure/Guidelines.md)
- Graph: "APIs SHOULD use resource-based designs with standard HTTP methods rather than operation resources."; "a function represents an operation that returns a single instance or collection of instances"; "An action might have side effects" — [Graph guidelines](https://github.com/microsoft/api-guidelines/blob/vNext/graph/GuidelinesGraph.md)

- Stripe action endpoints are `POST /v1/payment_intents/:id/cancel`, `/capture`, `/confirm`, `/increment_authorization`, `/apply_customer_balance`, `/verify_microdeposits` — [Stripe PaymentIntents](https://docs.stripe.com/api/payment_intents)

**Batch (by name / explicit list)**

- AIP-231 Batch Get: `GET ...:batchGet`; "The operation must be atomic: it must fail for all resources or succeed for all resources (no partial success)." — [AIP-231](https://google.aip.dev/231)
- AIP-233 Batch Create: `POST ...:batchCreate`, `requests` repeated field; "Synchronous batch create must be atomic."; "Asynchronous batch create may support atomic or partial success." — [AIP-233](https://google.aip.dev/233)

## How do the standards say state transitions, owned children (containment), polymorphism, file/media content and change feeds should be exposed?

### Takeaway

State: output-only enum, never writable through Update, changed by named transition methods that fail with a precondition error when invalid (AIP-216); Stripe and GitHub show the same pattern with POST sub-paths or PUT/DELETE toggles. Containment: child addressed only through the parent's URL, with explicit on-delete semantics and optional deep insert/update. Polymorphism: a discriminator field that is immutable after creation (Azure) or OData type inheritance with cast segments. Media: metadata entity plus a separate binary sub-resource (`/$value`, `/contents`) written with PUT/multipart. Change feeds: opaque delta links/tokens returning upserts plus tombstones (OData/Graph), or an append-only Event resource plus push delivery (Stripe/Zalando).

### Cited Findings

**State transitions**

- AIP-216: "Resources needing to communicate their state should use an enum, which should be called `State`"; the field should be "Output only"; "APIs should not allow a `State` enum to be directly updated through an "update" method"; ""Resting states" are lifecycle states that, absent user action, are expected to remain indefinitely."; ""Active states" are lifecycle states that typically resolve on their own into a single expected resting state." (e.g. "`CREATING` (usually becomes `ACTIVE`)"); "State transition methods are a special type of custom method"; "The name of the method should be a verb followed by the singular form of the resource's message name."; "If the state transition is not allowed, the service must error with `FAILED_PRECONDITION` (HTTP 400)."; "We use the term `State`, and not `Status`" — [AIP-216](https://google.aip.dev/216)
- AIP-134 repeats the rule from the Update side: "state fields must not be directly writable in update methods." — [AIP-134](https://google.aip.dev/134)
- AIP-128 `reconciling` output-only boolean for declarative resources whose actual state lags intended state — [AIP-128](https://google.aip.dev/128)
- Stripe PaymentIntent: statuses `requires_payment_method` → `requires_confirmation` → `requires_action` → `processing` → (`requires_capture`) → `succeeded` / `canceled`; failed attempt "returns to `requires_payment_method`"; "You can cancel a PaymentIntent before it reaches a `processing` or `succeeded` state. Cancellation ... can't be undone."; transitions are `POST /v1/payment_intents/:id/confirm|capture|cancel`; each transition emits an event such as `payment_intent.succeeded`, `payment_intent.canceled`, `payment_intent.requires_action` — [Stripe lifecycle](https://docs.stripe.com/payments/paymentintents/lifecycle), [Stripe PaymentIntents](https://docs.stripe.com/api/payment_intents)
- Stripe invoice objects carry a `status` plus a `status_transitions` object of timestamps (`finalized_at`, `marked_uncollectible_at`, `paid_at`, `voided_at`) — visible in the response sample at [Stripe create preview invoice](https://docs.stripe.com/api/invoices/create_preview)
- GitHub mixes two styles: writable state via `PATCH` (`"state": "closed"` with optional `state_reason`: `completed`, `not_planned`, `duplicate`, `reopened`) and toggle sub-resources via `PUT`/`DELETE` (`.../lock`), plus imperative `PUT .../merge` with a 405/409 failure when the transition is not possible — [GitHub issues](https://docs.github.com/en/rest/issues/issues), [GitHub pulls](https://docs.github.com/en/rest/pulls/pulls)
- OData: bound actions may be advertised per instance, and unavailability signalled by null, which lets a client discover currently valid transitions — [OData Protocol 4.01 §11.5.3](https://docs.oasis-open.org/odata/odata/v4.01/odata-v4.01-part1-protocol.html)
- Azure/Graph LRO status vocabularies (NotStarted/Running/Succeeded/Failed/Canceled; provisioning/deleting/succeeded) — [Azure guidelines](https://github.com/microsoft/api-guidelines/blob/vNext/azure/Guidelines.md), [Graph LRO pattern](https://github.com/microsoft/api-guidelines/blob/vNext/graph/patterns/long-running-operations.md)

**Owned children / containment**

- OData containment and canonical URL through the container; deep insert (all-or-nothing); deep update with nested delta (`PATCH` required); PUT of a collection deletes members not supplied; OnDelete Cascade/None/SetNull/SetDefault — see quotes in the first two key questions — [OData Protocol 4.01](https://docs.oasis-open.org/odata/odata/v4.01/odata-v4.01-part1-protocol.html), [CSDL XML 4.01](https://docs.oasis-open.org/odata/odata-csdl-xml/v4.01/odata-csdl-xml-v4.01.html)
- OData delete: "Services MUST implicitly remove relations to and from an entity when deleting it"; "Services MAY implicitly delete or modify related entities if required by integrity constraints." — [OData Protocol 4.01 §11.4.5](https://docs.oasis-open.org/odata/odata/v4.01/odata-v4.01-part1-protocol.html)
- AIP: one canonical parent (AIP-124); child delete protection via `force` (AIP-135); revisions as a nested sub-collection with cascading delete (AIP-162) — [AIP-124](https://google.aip.dev/124), [AIP-135](https://google.aip.dev/135), [AIP-162](https://google.aip.dev/162)
- AIP-144 offers the embedded alternative: a repeated field updated wholesale with Update, or `Add`/`Remove` custom methods, "If both of these strategies are too restrictive, consider using a subresource instead." — [AIP-144](https://google.aip.dev/144)
- Zalando [145]/[147]/[158]: nest only when the child cannot exist without the parent, limit depth, and "SHOULD allow optional embedding of sub-resources" (`embed`) — [Zalando guidelines](https://opensource.zalando.com/restful-api-guidelines/#145)
- Stripe embeds a bounded child list inside the parent as a list object with its own URL (`"lines": {"object": "list", "data": [], "has_more": false, "url": "/v1/invoices/in_.../lines"}`) — [Stripe create preview invoice](https://docs.stripe.com/api/invoices/create_preview)
- JSON:API compound documents: `GET /articles/1?include=comments.author`; "Every included resource object MUST be identified via a chain of relationships originating in a document's primary data." — [JSON:API 1.1](https://jsonapi.org/format/)

**Polymorphism** — see the derived/abstract findings in the first key question (OData inheritance + cast segment; Azure `kind` discriminator, immutable on PATCH; Graph type hierarchy vs facets vs flat bag; `$filter=isof(...)` in the Graph subsets pattern). Azure additionally requires polymorphic LRO status monitors to carry a required `kind` property — [Azure guidelines](https://github.com/microsoft/api-guidelines/blob/vNext/azure/Guidelines.md)

**File / media content** — see the media findings in the first key question. Summary of the surfaces: OData = `POST` binary to the entity set, `GET/PUT {entity}/$value`, stream properties as `PUT/DELETE {entity}/{prop}`; Stripe = `multipart/form-data` to a dedicated host, metadata `GET /v1/files/:id`, bytes `GET /v1/files/:id/contents`, expiring public `file_link`; Azure = pass storage references instead of bytes (BYOS). AIP-153's `:importX`/`:exportX` on a single resource is the AIP route for bulk payloads — [AIP-153](https://google.aip.dev/153)

**Change feeds**

- OData: "Clients request that the service track changes to a result by specifying the track-changes preference on a request."; "Delta links are opaque, service-generated links that the client uses to retrieve subsequent changes to a result."; "a delta response can contain deleted entities, new links, and deleted links."; "The client MUST NOT attempt to append system query options to the delta link."; "If the delta link is no longer valid, the service responds with 410 Gone" — [OData Protocol 4.01 §11.3](https://docs.oasis-open.org/odata/odata/v4.01/odata-v4.01-part1-protocol.html)
- Graph change tracking: "API designers can enable the change tracking (delta) capability on a resource"; `GET https://graph.microsoft.com/v1.0/users/delta`; `@odata.nextLink` for paging and `@odata.deltaLink` to "catch up on changes"; both "MUST be considered opaque URLs"; deleted items returned with id plus an `@removed` annotation — [Graph change-tracking pattern](https://github.com/microsoft/api-guidelines/blob/vNext/graph/patterns/change-tracking.md)
- Stripe: Event resource (list/retrieve only, 30-day retention) + push to configured event destinations; snapshot vs thin payloads — [Stripe Events](https://docs.stripe.com/api/events), [Stripe API v2 overview](https://docs.stripe.com/api-v2-overview)
- Zalando events: data change events must match API resources, carry explicit ordering, unique ids and mandatory metadata; consumers must tolerate duplicates ([214]) and out-of-order delivery ([212]) — [Zalando guidelines](https://opensource.zalando.com/restful-api-guidelines/#202)
- AIP: the fetched AIPs define no change-feed pattern; the nearest are `update_time` (AIP-148) and `etag` (AIP-154) — [AIP-148](https://google.aip.dev/148), [AIP-154](https://google.aip.dev/154)

### Inferences

- For `Workflow`, the standards converge on: output-only state enum; one named POST per transition; 400/409-class error on illegal transition; distinguish resting vs active (auto-resolving) states; optional per-instance advertisement of available transitions; transition timestamps (`status_transitions`) and one event per transition. The catalog description ("state machine with transitions") does not say whether active states, advertisement, timestamps or events are generated.
- A lighter "Stateful" trait (state enum + a few transition actions, without a full state-machine archetype) is what AIP-216 actually describes; AIP treats state as a *field pattern* (it sits in the "Fields" category), not as a resource kind.
- GitHub's `PUT`/`DELETE` on a fixed sub-path (`/lock`, `/starred/...`) is a distinct "idempotent boolean toggle" surface: PUT sets, DELETE clears, GET returns 204/404. It fits neither Action (POST) nor Association (resource with id) exactly.
- `Detail` should decide: (a) is the child ever addressable outside the parent URL (OData: no); (b) are children writable through the parent payload (deep insert/update) and is PUT-on-collection a replace-all; (c) on-delete behaviour.
- Polymorphism is orthogonal to every archetype (any Crud/Detail/Job could be polymorphic) → trait-like, but it changes DTO generation and EF mapping (TPH/TPT/TPC) more than endpoints. Azure's "discriminator immutable after create" and "no arrays of polymorphic objects on updatable resources" are generator-enforceable rules.
- Media has both forms: a whole resource that *is* a file (OData media entity, Stripe File → archetype) and a stream-valued property on an ordinary resource (OData `Edm.Stream` → trait/attribute).
- Change tracking has two forms: pull (delta token on the collection → trait on any listable resource) and push/log (Event resource + subscriptions → separate archetype plus a "publishes events" trait).

### Gaps

- No fetched source prescribes how a transition *history* (audit of state changes) should be exposed; Stripe's `status_transitions` timestamps are the only concrete example found.
- Stripe's webhook endpoint / event destination object schema and GitHub webhooks were not fetched.
- OData JSON batch `continue-on-error` details and OData 4.01 JSON delta payload format (`@removed`, `@id`) were not fetched from the JSON Format document.

## Which patterns are properties of a resource (traits) versus new resource shapes (archetypes)?

### Takeaway

A workable rule derived from the sources: a pattern is an **archetype** when it changes which standard methods exist, how the resource is identified/addressed, or its lifecycle (singleton, store, job, operation, media entity, association, event log, function/controller, anonymous write, contained child); it is a **trait** when it adds fields, request parameters, headers or extra custom methods that compose with any shape (etag, request id, soft delete, expiration, revisions, validate-only, filtering, pagination, field masks, expansion, batch, purge, import/export, change tracking, polymorphism, metadata). Google's own index mirrors this: shapes sit under "Resource Design" (121–129, 156, 236), composable behaviours under "Design Patterns" (152–165, 214, 217), with Jobs (152) the one "design pattern" that is really a resource shape.

### Cited Findings

**How the sources themselves classify**

- AIP index categories: Resource Design = 121, 122, 123, 124, 126, 128, 129, 156, 236; Operations = 130–136, 151, 231, 233, 234, 235; Fields includes 144 Repeated fields, 148 Standard fields, 203 Field behavior, 216 States; Design Patterns = 152 Jobs, 153 Import and export, 154 Resource freshness validation, 155 Request identification, 157 Partial responses, 158 Pagination, 159 Reading across collections, 160 Filtering, 161 Field masks, 162 Resource Revisions (Draft), 163 Change validation, 164 Soft delete, 165 Criteria-based delete, 210 Unicode, 211 Authorization checks, 214 Resource expiration, 217 Unreachable resources — [AIP index](https://google.aip.dev/general)
- Geewax's parts: "Resource relationships" (singleton sub-resources, cross references, association resources, polymorphism), "Collective operations" (copy/move, batch, anonymous writes, pagination, import/export), "Safety and security" (versioning, soft deletion, request deduplication, request validation, revisions, retrial, authentication) — [Simon & Schuster listing](https://www.simonandschuster.com/books/API-Design-Patterns/JJ-Geewax/9781617295850)
- Massé classifies only shapes (document, collection, store, controller) — [NBB wiki](https://github.com/NationalBankBelgium/REST-API-Design-Guide/wiki/REST-Resources-Single-items-and-collections)
- Graph's pattern list mixes type-modelling patterns (type hierarchy, facets, flat bag, dictionary, enums, evolvable enums, subsets, viewpoint, default properties, alternate key, namespace, navigation property) with behavioural ones (change tracking, long running operations, operations, upsert) — [Graph patterns directory](https://github.com/microsoft/api-guidelines/tree/vNext/graph/patterns)

**Trait-like patterns: evidence (fields/params/headers that compose with any resource)**

- Optimistic concurrency: AIP-154 "The etag field must be a string, and must be named `etag`."; mismatch → `ABORTED`; strong vs weak (`W/` prefix) — [AIP-154](https://google.aip.dev/154). OData: "Clients MUST specify the value returned in the ETag header, or star (*), in an If-Match header"; failure → 412 — [OData Protocol 4.01](https://docs.oasis-open.org/odata/odata/v4.01/odata-v4.01-part1-protocol.html). Azure: honour precondition headers, 304 on `If-None-Match` GET, `If-None-Match: *` for create-only — [Azure guidelines](https://github.com/microsoft/api-guidelines/blob/vNext/azure/Guidelines.md). Zalando [182]: `If-Match` + 412; "If-None-Match: * can be used ... to expose conflicts in resource creation." — [Zalando guidelines](https://opensource.zalando.com/restful-api-guidelines/#182)
- Idempotency: AIP-155 `request_id` ("Providing a request ID must guarantee idempotency."; duplicate → "return the response for the previously successful request") — [AIP-155](https://google.aip.dev/155). Stripe v1: `Idempotency-Key` on all POST, saved result replayed "including `500` errors", keys prunable after 24 hours, parameter mismatch errors; v2: POST and DELETE, 30-day window, failed work retried rather than replayed — [Stripe idempotent requests](https://docs.stripe.com/api/idempotent_requests), [Stripe API v2 overview](https://docs.stripe.com/api-v2-overview). Azure: `Repeatability-Request-ID` / `Repeatability-First-Sent`, tracked window "MUST be at least 5 minutes" — [Azure guidelines](https://github.com/microsoft/api-guidelines/blob/vNext/azure/Guidelines.md). Zalando [230] `Idempotency-Key` ("Keys expire after 24 hours"), [231] secondary business key → 409 on retry — [Zalando guidelines](https://opensource.zalando.com/restful-api-guidelines/#230)
- Soft delete (AIP-164), expiration (AIP-214: `expire_time` output, input-only `ttl`, in a `oneof expiration`), revisions (AIP-162), change validation (AIP-163) — [AIP-164](https://google.aip.dev/164), [AIP-214](https://google.aip.dev/214), [AIP-162](https://google.aip.dev/162), [AIP-163](https://google.aip.dev/163)
- Audit-style standard fields: `create_time`, `update_time`, `delete_time`, `expire_time`, `purge_time`, plus `uid` ("a system-assigned unique identifier"), `display_name`, `annotations` — [AIP-148](https://google.aip.dev/148). Zalando [174] common field names, [235] `created_at`-style timestamps — [Zalando guidelines](https://opensource.zalando.com/restful-api-guidelines/#174)
- Field behaviour modifiers: IDENTIFIER, IMMUTABLE ("cannot be changed after its creation"), INPUT_ONLY, OUTPUT_ONLY, OPTIONAL, REQUIRED, UNORDERED_LIST — [AIP-203](https://google.aip.dev/203)
- Server-modified values: "Fields must have a single owner, whether that is the client or the server."; "An attribute with an effective value must be expressed as two fields in the API" — [AIP-129](https://google.aip.dev/129)
- Filtering: AIP-160 single `string filter` with AND/OR/NOT, comparison operators, `.` traversal, `:` has, functions; invalid → `INVALID_ARGUMENT` — [AIP-160](https://google.aip.dev/160). OData `$filter` — [OData Protocol 4.01](https://docs.oasis-open.org/odata/odata/v4.01/odata-v4.01-part1-protocol.html). Azure `filter`, `orderby`, `top`, `skip`, `maxpagesize`, `select`, `expand` without `$` — [Azure guidelines](https://github.com/microsoft/api-guidelines/blob/vNext/azure/Guidelines.md). JSON:API reserves `filter` and `sort` (`?sort=-created,title`) — [JSON:API 1.1](https://jsonapi.org/format/). Zalando [137] `q`, `sort`, `fields`, `embed`, `offset`, `cursor`, `limit` — [Zalando guidelines](https://opensource.zalando.com/restful-api-guidelines/#137)
- Pagination: AIP-158 opaque `page_token`, optional `total_size`, `skip`; "Adding pagination to an existing RPC is a backwards-incompatible change." — [AIP-158](https://google.aip.dev/158). Azure `value` + `nextLink` — [Azure guidelines](https://github.com/microsoft/api-guidelines/blob/vNext/azure/Guidelines.md). Stripe v1 `limit`/`starting_after`/`ending_before`/`has_more`; v2 `page` token with `next_page_url`/`previous_page_url` — [Stripe pagination](https://docs.stripe.com/api/pagination), [Stripe API v2 overview](https://docs.stripe.com/api-v2-overview). Zalando [159] must paginate, [160] prefer cursors, [254] avoid total counts — [Zalando guidelines](https://opensource.zalando.com/restful-api-guidelines/#159)
- Partial responses / projection: AIP-157 field-mask side channel, or view enum with "BASIC and FULL"; List default BASIC — [AIP-157](https://google.aip.dev/157); AIP-161 update masks, no index addressing in repeated fields — [AIP-161](https://google.aip.dev/161); OData `$select`; JSON:API sparse fieldsets `fields[articles]=title,body`; Graph "Default properties" (omit non-default properties unless `$select`ed) — [OData Protocol 4.01](https://docs.oasis-open.org/odata/odata/v4.01/odata-v4.01-part1-protocol.html), [JSON:API 1.1](https://jsonapi.org/format/), [Graph guidelines](https://github.com/microsoft/api-guidelines/blob/vNext/graph/GuidelinesGraph.md)
- Expansion of related resources: OData `$expand` ("related entities and stream values that MUST be represented inline"); JSON:API `include`; Stripe `expand[]` (dot-nesting, "maximum depth of four levels", also requests non-default fields) and v2 `include`; Zalando [158] `embed` — [OData Protocol 4.01](https://docs.oasis-open.org/odata/odata/v4.01/odata-v4.01-part1-protocol.html), [JSON:API 1.1](https://jsonapi.org/format/), [Stripe expanding responses](https://docs.stripe.com/api/expanding_objects), [Zalando guidelines](https://opensource.zalando.com/restful-api-guidelines/#158)
- Alternate keys: OData `Employees(SSN='123-45-6789')`; Graph "Alternate key" pattern; AIP-162 `alternate_ids` on revisions — [URL Conventions 4.01 §4.3.5](https://docs.oasis-open.org/odata/odata/v4.01/odata-v4.01-part2-url-conventions.html), [Graph guidelines](https://github.com/microsoft/api-guidelines/blob/vNext/graph/GuidelinesGraph.md), [AIP-162](https://google.aip.dev/162)
- Computed properties: OData `$compute` ("Computed properties SHOULD be included as dynamic properties in the result") — [OData Protocol 4.01](https://docs.oasis-open.org/odata/odata/v4.01/odata-v4.01-part1-protocol.html)
- Deprecation signalling: Zalando [189] `Deprecation` and `Sunset` headers; Azure `azure-deprecating` header — [Zalando guidelines](https://opensource.zalando.com/restful-api-guidelines/#189), [Azure guidelines](https://github.com/microsoft/api-guidelines/blob/vNext/azure/Guidelines.md)

**Archetype-like patterns: evidence (method set / identity / lifecycle changes)** — Singleton (no Create/Delete), Store (PUT upsert with client key), Job (`:run` + executions), Operation (get/cancel/expire only), media entity (binary POST, `$value`), association (pair identity), Event (list/get only, retention), stateless/unbound operation (no resource), contained child (no top-level address), experiment (AIP-236): all quoted in the first key question.

### Inferences

- **Classification of catalog-missing items** (my inference; see table for the per-row mapping):
  - *Missing archetypes*: Media/File; Function/Query (safe, GET, optionally unbound); Unbound/stateless Operation; View/Aggregate (read model, `$apply`-style); Event log + subscription; Principal alias ("me"); WriteOnly/Ingest (anonymous writes); Operation/status monitor as distinct from re-runnable Job; Execution (job runs); Experiment/Draft (staged configuration with commit); Toggle (PUT/DELETE flag sub-resource).
  - *Missing traits*: Polymorphic (discriminator); Stateful (state enum + transition actions, lighter than Workflow); Validatable (`validate_only`) / Previewable; Purgeable (delete by criteria) and bulk update by criteria; Copyable / Movable / Renamable; Searchable (full-text `q`/`$search`, separate `/search`); CrossParent listing for `Under<Parent>` (`-` wildcard) with partial-success; Expandable (`include`/`expand`); Projectable (field mask / view / sparse fieldsets); Sortable and Paginated (if not already implicit in Crud); ChangeTracked (delta token); PublishesEvents; Extensible (metadata/annotations/labels, open type); AlternateKey; References\<T\> (cross reference with on-delete behaviour); Ordered (positional insert); LongRunning (any method may return an Operation / 202); Reconciling (declarative-friendly); Viewpoint (per-user state); HasStream (stream-valued property); DeepWrite (nested insert/update through the parent); AddRemove (atomic membership edits on a list field); Cascade/`force` delete; field-level modifiers (immutable / input-only / output-only / effective value).
- **MultiTenant is not defined as a pattern by any of the sources read.** Google models tenancy purely through the resource hierarchy (`projects/{project}/locations/{location}/...` in AIP-236 examples); Stripe uses an `account` attribute on events for connected accounts. It remains a Haldus-specific trait.
- **Auditable** is only partially backed: the standards give `create_time`/`update_time` (AIP-148) and `created_at` naming (Zalando); none of the fetched texts defines creator/updater identity fields.
- Several catalog traits are really *bundles* in the standards and may deserve sub-switches: SoftDeletable (undelete, expunge, show_deleted, purge_time), Revisioned (alias, rollback, revision-scoped children), Batch (get vs mutate; atomic vs partial/207; generic cross-resource `$batch`/atomic-operations endpoint), Idempotent (replay vs retry semantics, key retention, parameter fingerprint), Versioned (etag in body vs `If-Match` header; `If-None-Match: *` create guard; etag on actions and deletes).
- AIP-128 shows traits can conflict: declarative-friendly resources "should not employ custom methods", "should not implement soft-delete" and must use Update rather than Add/Remove. A trait compatibility matrix is implied by the standard itself.
- Borderline cases: **Jobs** — archetype (AIP files it under design patterns, but it prescribes a resource name suffix, a full method set and a sub-resource). **Revisions** — trait that *generates* a secondary read-only child resource. **Association** — archetype when it carries its own id/metadata (AIP-124 sub-resource, Geewax ch. 14); trait-like relationship endpoint when it is only linkage (JSON:API `relationships/x`, OData `$ref`, AIP-144 add/remove). **Polymorphism** — trait at the API level, but with archetype-scale impact on entity/ORM generation.

### Gaps

- I did not inspect the Haldus codebase or specs; "closest catalog item" is judged from the one-line descriptions in the brief. Rows marked PARTIAL need confirmation against actual generator behaviour.
- Not researched: authorization/permission patterns (AIP-211), versioning (AIP-185, Azure `api-version`, `Stripe-Version`) beyond incidental quotes, error models (AIP-193, RFC 9457), rate limiting; these are cross-cutting but outside "resource kinds / method kinds / patterns" as scoped.
- Zalando text beyond ~200k characters (events chapter bodies, appendices) and the last ~9k characters of the Azure guidelines were not read; rule titles for those parts come from the table of contents only.
