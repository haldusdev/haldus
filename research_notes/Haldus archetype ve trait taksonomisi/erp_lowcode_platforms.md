## What exact kinds does each platform define, and what does each kind change about storage, API surface and lifecycle?

### Takeaway
All five platforms have a small closed set of "kinds" that are chosen at entity-definition time and are mostly immutable afterwards; the kind switches storage (own table / shared key-value table / no table / external source / separate draft table), ownership and security model, and which lifecycle verbs exist (submit/cancel, activate/deactivate, edit-draft/activate). Kinds that our catalog has no archetype for: virtual/external entity, tree, activity, transient/wizard, event, abstract/mixin model, inheritance/delegation, and draft-enabled entity.

### Cited Findings

#### Frappe Framework / ERPNext

Kinds (DocType flags):

- DocType is the single modelling unit: "A DocType is the core building block of any application based on the Frappe Framework." "It describes the Model and the View of your data." Table names are prefixed with `tab`. [F] — [Frappe: DocTypes](https://docs.frappe.io/framework/user/en/basics/doctypes)
- **Single (Is Single)**: "A Single DocType is a DocType that has only one instance in the database." "It is useful for persisting things like System Settings, which don't make sense to have multiple records." Storage differs: "Single DocTypes are stored in the `tabSingles` table in the database, with each property having its own record." [F] — [Frappe: Single DocType](https://docs.frappe.io/framework/user/en/basics/doctypes/single-doctype)
- **Child (Is Child Table)**: "A Child DocType is doctype which can only be linked to a parent DocType." "To make a Child DocType make sure to check Is Child Table while creating the doctype." "Child DocType records are directly attached to the parent doc." Extra columns: `parent` ("name of the parent"), `parenttype` ("DocType of the parent"), `parentfield` ("Field in the parent that links this child to it"), `idx` ("Sequence (row)"). [F] — [Frappe: Child DocType](https://docs.frappe.io/framework/user/en/basics/doctypes/child-doctype)
- **Submittable (Is Submittable)**: "When you enable Is Submittable in a DocType is becomes a Submittable DocType." Documents move through Draft, Submitted, Cancelled; submitted documents cannot have field values changed; a cancelled document can be amended and the new document links back through the Amended From field. [F] — [Frappe tutorial: Types of DocType](https://docs.frappe.io/framework/user/en/tutorial/types-of-doctype.md)
- **Master vs Transactional** is a documented (informal) classification of linked DocTypes: Master = entities such as Article or Library Member; Transactional = records of activity such as Library Membership. [F] — [Frappe tutorial: Types of DocType](https://docs.frappe.io/framework/user/en/tutorial/types-of-doctype.md)
- **Virtual (Is Virtual)**: "Virtual DocType is a feature-extension for DocType which allows developers to create DocTypes with custom data sources"; purpose is "to define custom DocTypes in the system without creating a table in the database"; the source "can be anything: an external API, a secondary database, JSON or CSV files, etc."; they "function exactly like normal DocTypes in the frontend"; "All the /api/resource methods defined by the framework are compatible with Virtual DocTypes." The example controller implements `db_insert`, `load_from_db`, `db_update`, `delete`, `get_list`, `get_count`, `get_stats`. Limitation: "`frappe.db.*` calls work only with site's database connection." [F] — [Frappe: Virtual DocType](https://docs.frappe.io/framework/user/en/basics/doctypes/virtual-doctype)
- **Tree (Is Tree)**: a DocType gets a tree view when "Is Tree" is enabled, which means it has an `is_group` field and nested-set fields `lft` and `rgt`. [S] — [Frappe: Tree view](https://docs.frappe.io/framework-git/client-side/tree-view)

Field/relationship kinds:

- **Link**: "Link field is connected to another master from where it fetches data." **Dynamic Link**: "Dynamic Link field is one which can search and hold value of any document/doctype." **Table**: "With a "Table" field, you can render another DocType as a child table within your form." **Table MultiSelect**: "This is a combination of 'Link' type and 'Table' type fields." Other special types listed: Attach, Attach Image, Attachment Gallery, Signature, Geolocation, Rating, Duration, JSON, Barcode, Password, Read Only ("will carry data fetched from another form which will be non-editable"). [F] — [Frappe: Field types](https://docs.frappe.io/framework/user/en/basics/doctypes/fieldtypes)
- Conditional field behaviour: Mandatory Depends On — "If this condition is satisfied, the field will be mandatory."; Read Only Depends On — "If this condition is satisfied, the field will be read only." [F] — [Frappe: DocField](https://docs.frappe.io/framework/user/en/basics/doctypes/docfield)

Cross-cutting behaviours:

- **Naming** (9 methods): Set by user; Autoincrement ("The system generates a sequential numeric name by incrementing the last created document"; deleted numbers are not reused); By fieldname ("The value in the selected field must always be unique."); By "Naming Series" field (`PRE.#####` -> `PRE00001`, the series can differ per document); Expression (`PRE-.#####`, with date parts `MM`, `YYYY`, `DD`, `WW`, `timestamp`, field values and `#####` counters); Expression (Old Style) — "This method is deprecated and will be removed in version 16."; Random; UUID ("randomly generated ... UUID v4"); By script (`autoname` controller method). **Document Naming Rule**: "You can create multiple Document Naming Rules for a particular doctype that can be applied selectively based on filters", each with a priority, conditions, prefix and digit count. Special rules: "Child DocTypes do not follow naming rules"; "Amended documents have a suffix (`-1`, `-2` etc) to the original document". [F] — [Frappe: Naming](https://docs.frappe.io/framework/user/en/basics/doctypes/naming)
- **Controller hooks**: `before_insert`, `validate` ("Use this method to throw any validation errors and prevent the document from saving."), `before_save`, `on_update`, `before_submit`, `on_submit`, `before_cancel`, `on_cancel`, `on_trash`, `after_delete`, `before_update_after_submit`, `on_update_after_submit`, `on_change`, `before_rename`, `after_rename`, `before_naming`, `autoname`. Note the rename hooks: the primary key (`name`) is renameable. [F] — [Frappe: Controllers](https://docs.frappe.io/framework/user/en/basics/doctypes/controllers)
- **Track Changes -> Version**: off by default, enabled per DocType (`track_changes` = 1); on save Frappe compares with the prior version and writes a Version record holding only changed fields (`ref_doctype`, `docname`, JSON `data`). [S] — [Frappe: Audit trail](https://docs.frappe.io/framework-git/security/audit-trail)
- **Sharing**: a `Shared`/`Unshared` comment is written alongside the `DocShare` record. [S] — [Frappe: Audit trail](https://docs.frappe.io/framework-git/security/audit-trail.md)
- **User Permissions** (row-level restriction by linked value): "User permissions is a way of restricting user access to particular documents."; "If Applicable For is not set, User Permission will apply across all related Document Types."; Is Default — "Only a single user permission can be set as default for a particular document type for a specific user."; for tree DocTypes, Hide Descendants — "By enabling this checkbox, permissions for descendants of For Value will not be granted." [F] — [ERPNext: User Permissions](https://docs.frappe.io/erpnext/user/manual/en/user-permissions)

#### Odoo (19.0)

Kinds (model classes):

- **AbstractModel**: alias of `BaseModel`, for "abstract super classes meant to be shared by multiple inheriting models" — no table. **Model**: "Main super-class for regular database-persisted Odoo models." **TransientModel**: "Model super-class for transient records, meant to be temporarily persistent, and regularly vacuum-cleaned."; "A TransientModel uses the same access rights mechanisms as a regular Model."; limits `_transient_max_count` / `_transient_max_hours`; "Actual cleaning will happen only once every 5 minutes". [F] — [Odoo 19 ORM API](https://www.odoo.com/documentation/19.0/developer/reference/backend/orm.html)
- Model attributes that act as kind switches: `_auto` ("Whether a database table should be created."), `_abstract`, `_transient`, `_log_access` (automatic access-log fields; defaults to `_auto`), `_parent_store` (compute `parent_path`), `_parent_name` (default `'parent_id'`), `_rec_name`, `_order`, `_check_company_auto`, `_inherit`, `_inherits`, `_fold_name`, `_table`, `_register`. [F] — [Odoo 19 ORM API](https://www.odoo.com/documentation/19.0/developer/reference/backend/orm.html)
- **Three inheritance mechanisms**: Classical — "When using the `_inherit` and `_name` attributes together, Odoo creates a new model using the existing one"; Extension — "When using `_inherit` but leaving out `_name`, the new model replaces the existing one, essentially extending it in-place."; Delegation (`_inherits`) — the model "delegates the lookup of any field not found on the current model to "children" models" and "the new model exposes all the fields of the inherited models but stores none of them." [F] — [Odoo 19 ORM API](https://www.odoo.com/documentation/19.0/developer/reference/backend/orm.html)

Field/relationship kinds:

- **Many2one** (`ondelete` takes 'set null', 'restrict', 'cascade'); **One2many** (requires `comodel_name` and `inverse_name`, the inverse Many2one); **Many2many** (relation table and columns auto-generated); **Reference** — "The field value is stored as a string following the pattern "res_model,res_id" in database."; **Many2oneReference** — stored as an integer id, with `model_field` naming the Char field holding the model name. [F] — [Odoo 19 ORM API](https://www.odoo.com/documentation/19.0/developer/reference/backend/orm.html)
- **Computed / related / inverse**: computed fields are not stored by default and are "readonly by default" unless an inverse is given; related fields are not stored, not copied, read-only by default and computed in superuser mode. `copy` is a per-field parameter. [F] — [Odoo 19 ORM API](https://www.odoo.com/documentation/19.0/developer/reference/backend/orm.html)
- **company_dependent**: "The value is stored on the model table as jsonb dict with the company id as the key." [F] — [Odoo 19 ORM API](https://www.odoo.com/documentation/19.0/developer/reference/backend/orm.html)
- **translate** on Char/Text enables "the translation of the field's values". [F] — [Odoo 19 ORM API](https://www.odoo.com/documentation/19.0/developer/reference/backend/orm.html)
- **Reserved field names**: `name` (default `_rec_name`), `active` (toggles "the global visibility of the record."), `state` (lifecycle stages of the object), `parent_id` (default `_parent_name`), `parent_path` (stores the tree structure when `_parent_store` is True), `company_id` ("Main field name used for Odoo multi-company behavior."). **Automatic fields**: `id`, `display_name`, `create_date`, `create_uid`, `write_date`, `write_uid`. [F] — [Odoo 19 ORM API](https://www.odoo.com/documentation/19.0/developer/reference/backend/orm.html)
- **Constraints**: `models.Constraint("CHECK (x > y)", ...)`, Index, UniqueIndex as class attributes; `@api.constrains` is "Invoked on the records on which one of the named fields has been modified." `copy()` — "Duplicate record `self` updating it with default values." [F] — [Odoo 19 ORM API](https://www.odoo.com/documentation/19.0/developer/reference/backend/orm.html)

Mixins:

- **mail.thread** (chatter): followers, `message_post()`, `message_subscribe()`, field change tracking via `tracking=True`, notification subtypes ("Subtypes act as a classification system for notifications, allowing subscribers to a document to customize" what they receive). **mail.alias.mixin**: "Alias support is added by inheriting `mail.alias.mixin`" (one `mail.alias` per record; inbound email creates/updates records). **mail.activity.mixin**: "You can integrate activities using the `mail.activity.mixin` class on your object." (`activity_ids`). **utm.mixin**: "can be used to track online marketing/communication campaigns" (`campaign_id`, `source_id`, `medium_id`). **website.published.mixin**: `website_published`, `website_url`. **website.seo.metadata**: `website_meta_title/description/keywords`. **rating.mixin**: "allows sending email to ask for customer rating" (`rating.rating` records). [F] — [Odoo 19 Mixins and Useful Classes](https://www.odoo.com/documentation/19.0/developer/reference/backend/mixins.html)
- **portal.mixin** (`_name = 'portal.mixin'`, "Portal Mixin"): fields `access_url` ("Customer Portal URL"), `access_token`, `access_warning`; methods `_portal_ensure_token`, `_get_share_url`, `action_share`, `get_portal_url`. Not in the developer reference; taken from source. [F] — [odoo/odoo 19.0 portal_mixin.py](https://github.com/odoo/odoo/blob/19.0/addons/portal/models/portal_mixin.py)
- **Multi-company**: with `_check_company_auto = True`, "On each create() and write(), automatic checks will be triggered to ensure the multi-company consistency of the record."; reading a company-dependent field uses the current company; record rules are based on the user's active companies. [S] — [Odoo 19 Multi-company Guidelines](https://www.odoo.com/documentation/19.0/developer/howtos/company.html)

#### Salesforce

- **Relationship kinds**: Lookup — "This type of relationship links two objects, but has no effect on deletion or security. Unlike master-detail fields, lookup fields aren't automatically required."; Master-detail — "A parent-child relationship in which the master object controls certain behaviors of the detail object."; "The detail record inherits the sharing and security settings of its master record."; Many-to-many — "Create a custom junction object with two master-detail relationship fields, each linking to the objects you want to relate."; external objects — "Only lookup, external lookup, and indirect lookup relationships are available for external objects." [S] — [Salesforce Object Reference: Relationships Among Objects](https://developer.salesforce.com/docs/atlas.en-us.object_reference.meta/object_reference/relationships_among_objects.htm)
- Lookup: "A lookup relationship essentially links two objects together so that you can "look up" one object" from the other. Master-detail: "The master object controls certain behaviors of the detail object, like who can view the detail's data."; "if a record on the master object is deleted, all its related detail records are deleted as well." **Hierarchical**: "Hierarchical relationships are a special type of lookup relationship." and are "only available on the User object." [F] — [Trailhead: Object Relationships](https://trailhead.salesforce.com/content/learn/modules/data_modeling/object_relationships)
- **Polymorphic lookups**: a polymorphic field is one where the related object "might be one of several different types of objects"; Task `Who` can be a Contact or Lead, `What` "represents nonhuman objects"; queried with `TYPEOF` in SOQL. [S] — [SOQL: Relationship Fields and Polymorphic Fields](https://developer.salesforce.com/docs/platform/salesforce-soql-sosl/guide/sforce-api-calls-soql-relationships-and-polymorph-keys.html)
- Task and Event: "In the user interface, Task and Event records are collectively referred to as activities."; Task `AccountId` is derived from `WhatId`/`WhoId`. [S] — [Salesforce Object Reference: Task](https://developer.salesforce.com/docs/atlas.en-us.api.meta/api/sforce_api_objects_task.htm)
- **Big objects** (`__b`): "In the API, the names of custom big objects have a suffix of two underscores immediately followed by a lowercase "b" (__b)."; defined with fields plus an index; support only object and field permissions (no sharing rules); triggers, flows and processes are not supported; up to 100 big objects per org. [S] — [Salesforce Big Objects: Define and Deploy](https://developer.salesforce.com/docs/atlas.en-us.bigobjects.meta/bigobjects/big_object_define.htm)
- **External objects** (`__x`): names "are identified by a suffix of two underscores immediately followed by a lowercase "x""; they resemble custom objects but records live in another system and are fetched on demand through Salesforce Connect adapters (OData, cross-org, custom Apex adapter). External lookup links to an external object; indirect lookup links an external object to a standard/custom object through a unique external ID field on the parent. [S] — [Salesforce Object Reference: External Objects](https://developer.salesforce.com/docs/atlas.en-us.object_reference.meta/object_reference/sforce_api_objects_external_objects.htm); [Trailhead: Create an Indirect Lookup Relationship](https://trailhead.salesforce.com/content/learn/projects/quickstart-lightning-connect/quickstart-lightning-connect3)
- **Platform events** (`__e`): "the system appends the __e suffix to create the API name of the event."; "you publish events in the same way that you insert sObjects."; "you can't query them through SOQL or SOSL."; "Salesforce stores high-volume platform events for 72 hours in the event bus."; publish behaviour is either Publish Immediately ("a subscriber can sometimes receive the event message before the data is committed.") or Publish After Commit; "Each event message is assigned an opaque ID contained in the ReplayId field." [F] — [Trailhead: Define and Publish Platform Events](https://trailhead.salesforce.com/content/learn/modules/platform_events_basics/platform_events_define_publish)
- **Custom metadata types** (`__mdt`): "A custom metadata type is an object that's used to define the structure for application metadata."; "The records of custom metadata types are also metadata, not data."; "Records can be packaged and deployed." **Custom settings** can be "list- based or hierarchy-based"; for custom settings "Records can't be deployed using a package, Metadata API, or change sets."; custom metadata types do not "support hierarchy type data based on user, profile, or org level." [F] — [Trailhead: Custom Metadata Types overview](https://trailhead.salesforce.com/content/learn/modules/custom_metadata_types_dec/cmt_overview)
- **Roll-up summary fields** exist only on the master side of a master-detail relationship; calculations are COUNT, SUM, MIN, MAX. [S] — [Trailhead: Roll-Up Summary Fields](https://trailhead.salesforce.com/content/learn/modules/point_click_business_logic/roll_up_summary_fields)
- **Ownership**: detail records in master-detail relationships are the one case without an Owner field; sharing rules, manual sharing and queues require the Owner field and so are unavailable there. [S] — [Salesforce Developers Blog: Behind the Scenes of Record Ownership](https://developer.salesforce.com/blogs/2013/10/behind-the-scenes-of-record-ownership-in-salesforce)

- **Lookup kinds**: Simple; Customer ("a single reference to either an account or a contact row"); Owner ("a single reference to either a team or a user row. [F] — [Microsoft Learn: Column data types](https://learn.microsoft.com/en-us/power-apps/maker/data-platform/types-of-fields)

[F] — [Microsoft Learn: Column data types](https://learn.microsoft.com/en-us/power-apps/maker/data-platform/types-of-fields)
- **Per-table capability switches** (advanced options): Apply duplicate detection rules; Track changes ("Enables data synchronization in a performant way by detecting what data has changed since the data was initially extracted or last synchronized."); Audit changes to its data (per-column enablement); Enable long term retention; Creating a new activity ("Associate activities to records for this table."); Can have connections; Can have a contact email; Have an access team; Can be linked to feedback (feedback/ratings on any record); Appear in search results; Can be taken offline; Can be added to a queue ("Queues improve routing and sharing of work"); Enable Attachments ("append notes and files to records for this table"); SharePoint document management; mail merge. [F] — [Microsoft Learn: Create and edit tables](https://learn.microsoft.com/en-us/power-apps/maker/data-platform/create-edit-entities-portal)
- **Connections** as an informal relationship kind: "There are other less formal kinds of relationships between rows that are called connections." [F] — [Microsoft Learn: Table relationships](https://learn.microsoft.com/en-us/power-apps/maker/data-platform/create-edit-entity-relationships)
- **Elastic tables**: partitioned on a system `PartitionId` column; "Dataverse automatically includes a Time to live integer column with elastic tables" (`TTLInSeconds`); "Elastic tables don't support multi-record transactions." [S] — [Microsoft Learn: Elastic tables for developers](https://learn.microsoft.com/power-apps/developer/data-platform/elastic-tables)
- **Rollup columns**: aggregate over related child rows of a 1:N relationship (sum, count, min, max, avg), calculated asynchronously on a schedule, read-only. [S] — [Microsoft Learn training: Create a rollup column](https://learn.microsoft.com/en-us/training/modules/create-define-calculation-rollup-fields/2-rollup)

#### SAP RAP / CDS

- **Business object and composition tree**: "A RAP BO is based on a special, tree-like hierarchical structure of CDS entities of a data model"; "The top parent entity of a CDS composition tree is the root entity that represents the business object."; parent and child entities are defined "using CDS compositions and to-parent associations". "A BDEF defines the behavior of a RAP BO". [F] — [SAP-samples ABAP cheat sheets: ABAP for RAP (EML)](https://github.com/SAP-samples/abap-cheat-sheets/blob/main/08_EML_ABAP_for_RAP.md)
- **Implementation types**: managed — "The managed RAP BO provider fully or partly provides the transactional buffer and RAP BO behavior"; unmanaged — "Everything must be provided by the unmanaged RAP BO provider"; hybrids — "it is possible to have a managed RAP BO with unmanaged parts, e.g. unmanaged save or additional save" (additional save "enhances the default save sequence by incorporating additional save logic"; unmanaged save "replaces the default managed save logic with a custom save logic"). [F] — [SAP-samples ABAP cheat sheets: ABAP for RAP (EML)](https://github.com/SAP-samples/abap-cheat-sheets/blob/main/08_EML_ABAP_for_RAP.md)
- **Actions**: "A RAP action is a non-standard operation that modifies the state of a RAP BO entity instance." [F] — [SAP-samples ABAP cheat sheets](https://github.com/SAP-samples/abap-cheat-sheets/blob/main/08_EML_ABAP_for_RAP.md). Variants: an action is instance-bound by default; `static` makes it "not bound to any instance of a RAP BO entity but relates to the complete entity"; **factory actions** "are used to create RAP BO entity instances" and can be instance-bound (`factory action copy_instance [1];`) or static (`static factory action new_instance [1];`); `internal action` is callable only from inside the BO; `use action` exposes an action in a projection. [S] — [SAP Developers tutorial: RAP100 factory action](https://developers.sap.com/tutorials/abap-environment-rap100-factory-action.html); [SAP Learning: Defining Actions and Messages](https://learning.sap.com/courses/building-transactional-apps-with-the-abap-restful-application-programming-model/defining-actions-and-messages)
- **Transactional phases**: interaction phase = "the data reading and modification phase"; save sequence methods `finalize` ("For final calculations and data modifications involving all BOs in the current RAP transaction"), `check_before_save` ("Checks the consistency of the transactional buffer before the save method saves data to the database"), `adjust_numbers` ("Preliminary IDs are mapped to final keys. Only for late numbering."), `save`, `cleanup`. Determinations "specified with `ON SAVE`" run in finalize; validations "specified with `ON SAVE`" run in check_before_save. [F] — [SAP-samples ABAP cheat sheets](https://github.com/SAP-samples/abap-cheat-sheets/blob/main/08_EML_ABAP_for_RAP.md)
- **Numbering**: early — "The final key values are assigned during a RAP create operation in the interaction phase."; late — "The final key values are assigned during the RAP save sequence"; internal — "Key values are provided by the RAP BO provider."; `%pid` is "only available in late numbering scenarios"; `%cid` is a content ID used to reference not-yet-keyed instances in the same request. [F] — [SAP-samples ABAP cheat sheets](https://github.com/SAP-samples/abap-cheat-sheets/blob/main/08_EML_ABAP_for_RAP.md)
- "Late numbering is used for scenarios that need gap-free numbers."; "Managed Internal Numbering is only supported in managed implementation scenarios and when the primary key is a single UUID-based field." [S] — [SAP Learning: Setting Values Using Numbering and Determinations](https://learning.sap.com/courses/building-transactional-apps-with-the-abap-restful-application-programming-model/setting-values-using-numbering-and-determinations); [SAP Developers tutorial: RAP100 early numbering](https://developers.sap.com/tutorials/abap-environment-rap100-early-numbering.html)
- **Concurrency**: pessimistic — "exclusively locking data sets for the time that a modification request is executed"; "In managed scenarios, the business object framework assumes all locking tasks."; optimistic — "Concurrency control based on ETags does not lock the data set."; "ETag handling is activated by adding etag master to the behavior definition of the root entity."; sub-entities "can be defined with addition etag dependent", in which case "instances of that sub entity are not protected with an ETag field of their own" and "they refer to an ETag master entity further up the hierarchy, for example the root entity"; recommended ETag field is "a timestamp field of type abp_lastchange_tstmpl". [F] — [SAP Learning: Understanding Concurrency Control](https://learning.sap.com/courses/building-transactional-apps-with-the-abap-restful-application-programming-model/understanding-concurrency-control)
- **Other BDEF properties**: permissions "cover aspects such as global and instance authorization"; feature control (global, instance, static) defines "which data is mandatory and which is read-only"; business events are raised with `RAISE ENTITY EVENT` "typically in the save phase". [F] — [SAP-samples ABAP cheat sheets](https://github.com/SAP-samples/abap-cheat-sheets/blob/main/08_EML_ABAP_for_RAP.md)

### Inferences
- The "kind" is consistently a compile-time/definition-time choice that cannot be changed after data exists (Dataverse ownership and activity type explicitly; Frappe autoincrement naming only with zero documents). This matches the Haldus design where the archetype is chosen in the `Map*<T>()` call.
- Three distinct things hide behind "kind" on these platforms, and they are orthogonal: (1) storage strategy (own table / key-value singleton / none-virtual / external / high-volume store / temp), (2) position in an ownership graph (root, owned child, junction), (3) lifecycle model (free CRUD / submit-cancel / active-inactive / draft-activate / event publish-only). Our archetype list mixes all three axes in one flat list, which is why combinations such as "submittable tree" or "virtual read-only lookup" are not expressible.
- Odoo's AbstractModel is the platform equivalent of a user-defined trait (a reusable bundle of fields and behaviour with no table). Our catalog has built-in traits only; user-authored traits are not listed.
- Dataverse's activity tables and Odoo's `_inherits` are both table-per-type inheritance with a shared base row (ActivityPointer / the delegated parent record). No archetype or trait in our catalog expresses "entity is a subtype of a base entity and appears in the base list".
- Dataverse's new `Filtered` ownership (preview) and Frappe's User Permissions are the same idea: row access decided by the value of a column rather than by an owner. This is a different axis from MultiTenant.

No help.sap.com URL is cited.

## How does each platform model an Order with OrderItems (owned children), and what rules are inherited from the parent?

### Takeaway
Every platform distinguishes an owned child from an ordinary foreign key, and the child inherits a recurring bundle from its parent: cascade delete, security/sharing, ownership (the child has no owner of its own), and concurrency token/lock. Salesforce and Dataverse additionally allow only a constrained number of "parental" relationships and expose reparenting as an explicit option.

### Cited Findings
- **Frappe**: a Table field on the parent points to a Child DocType; rows carry `parent`, `parenttype`, `parentfield`, `idx` and "are directly attached to the parent doc" (returned as a list inside the parent). Children have no naming rules of their own ("Child DocTypes do not follow naming rules"). [F] — [Frappe: Child DocType](https://docs.frappe.io/framework/user/en/basics/doctypes/child-doctype); [Frappe: Naming](https://docs.frappe.io/framework/user/en/basics/doctypes/naming)
- **Frappe** also has a child-table-backed multi-select: Table MultiSelect "is a combination of 'Link' type and 'Table' type fields." [F] — [Frappe: Field types](https://docs.frappe.io/framework/user/en/basics/doctypes/fieldtypes)
- **Odoo**: there is no child model kind; a One2many on the order requires the inverse Many2one on the line, and the Many2one's `ondelete` ('set null', 'restrict', 'cascade') decides ownership semantics. [F] — [Odoo 19 ORM API](https://www.odoo.com/documentation/19.0/developer/reference/backend/orm.html)
- **Salesforce**: master-detail. "if a record on the master object is deleted, all its related detail records are deleted as well."; the master controls "who can view the detail's data". [F] — [Trailhead: Object Relationships](https://trailhead.salesforce.com/content/learn/modules/data_modeling/object_relationships). "The detail record inherits the sharing and security settings of its master record." [S] — [Salesforce Object Reference: Relationships Among Objects](https://developer.salesforce.com/docs/atlas.en-us.object_reference.meta/object_reference/relationships_among_objects.htm). The detail has no Owner field. [S] — [Salesforce Developers Blog: Record Ownership](https://developer.salesforce.com/blogs/2013/10/behind-the-scenes-of-record-ownership-in-salesforce). Roll-up summary fields (COUNT/SUM/MIN/MAX) live on the master. [S] — [Trailhead: Roll-Up Summary Fields](https://trailhead.salesforce.com/content/learn/modules/point_click_business_logic/roll_up_summary_fields)
- **Dataverse, option 1 — parental relationship**: "A parental table relationship is any 1:N table relationship where one of the cascading options in the Parental column ... is true" (Assign, Delete, Reparent, Share, Unshare set to a cascading value). "Usually this means that for each table pair there's only one parental relationship."; new relationships cannot cascade if the related table already has a cascading relationship — "This prevents relationships that create a multi-parent relationship." [F] — [Microsoft Learn: Table relationships](https://learn.microsoft.com/en-us/power-apps/maker/data-platform/create-edit-entity-relationships)
- **Dataverse cascade matrix**: actions Assign, Delete, Merge, Reparent, Share, Unshare (plus Rollup View in the maker UI); values Cascade All, Cascade Active, Cascade User Owned, Cascade None, Remove Link, Restrict. Delete allows only Cascade / RemoveLink / Restrict. "The reparent action is similar to the share action, but it deals with inherited access rights instead of explicit access rights." [F] — [Microsoft Learn: Configure table relationship cascading behavior](https://learn.microsoft.com/en-us/power-apps/developer/data-platform/configure-entity-relationship-cascading-behavior)
- **Dataverse, option 2 — child table** (`IsChildEntity`): no privileges of its own, never user/team owned, operations allowed only if the same operation is allowed on the parent, deleted automatically with the parent. [F] — [Microsoft Learn: Work with table definitions](https://learn.microsoft.com/en-us/power-apps/developer/data-platform/entity-metadata)
- **Dataverse N:N**: "depends on a special Relationship table, sometimes called an Intersect table"; rows "can be considered peers and the relationship is reciprocal." [F] — [Microsoft Learn: Table relationships](https://learn.microsoft.com/en-us/power-apps/maker/data-platform/create-edit-entity-relationships)
- **SAP RAP**: the item is a child entity in the composition tree of the order root; sub-entities defined as `etag dependent` have no ETag of their own and "refer to an ETag master entity further up the hierarchy, for example the root entity". [F] — [SAP Learning: Understanding Concurrency Control](https://learning.sap.com/courses/building-transactional-apps-with-the-abap-restful-application-programming-model/understanding-concurrency-control). The BDEF lock clause has the form `lock master | dependent`, propagating locks between root and child nodes. [S] — [ABAP keyword docs mirror (7.54): BDL lock](https://eduardocopat.github.io/abap-docs/7.54/abenbdl_lock) (unofficial mirror, old release; low reliability)
- **Salesforce junction**: a junction object is a custom object with two master-detail fields. [S] — [Salesforce Object Reference: Relationships Among Objects](https://developer.salesforce.com/docs/atlas.en-us.object_reference.meta/object_reference/relationships_among_objects.htm)

### Inferences
- The inherited bundle is: (a) cascade delete, (b) authorization from the parent (Salesforce "Controlled by Parent", Dataverse child tables, RAP authorization dependent), (c) no independent owner, (d) shared concurrency token and lock (RAP etag/lock dependent), (e) lifecycle state (Frappe child rows are frozen with the submitted parent; RAP draft covers the whole composition tree), (f) parent-level aggregates (roll-up summary). Our `Detail` archetype should state explicitly which of these it implies; `Under<Parent>` (nested independent child) corresponds to Salesforce lookup / Dataverse referential relationships where none of the bundle is inherited.
- `Versioned` + `Detail` interplay is a documented concern on SAP (etag master/dependent): changing an OrderItem must invalidate the Order's ETag. Our catalog does not say whether a Detail change bumps the parent version.
- Row ordering of children (`idx` in Frappe) is a built-in property of owned children on Frappe; our catalog has no ordering/sequence trait.
- Reparenting (moving a child to another parent) is an explicit, off-by-default capability on Salesforce and a configurable cascade action on Dataverse; it is a missing option on `Detail`/`Under<Parent>`.
- Delete behaviour of non-owning references is a first-class setting (Odoo `ondelete`, Dataverse Restrict / Remove Link / Cascade). Our catalog has no "reference with on-delete rule" concept.

### Gaps
- Frappe's docs page for child DocTypes contains no statement on child permissions or on child docstatus; the claim that child rows inherit the parent's permissions and docstatus is general knowledge, not sourced here.
- Salesforce "Allow reparenting" and "Controlled by Parent" org-wide default wording could not be fetched from help.salesforce.com; a search snippet of a third-party source says "Administrators can allow child records to be reparented by selecting the Allow reparenting option", which I do not treat as a primary citation.
- RAP `create by association` (deep create of children through the parent) and authorization master/dependent were not found in a readable official page.

## How does each platform model document lifecycles that are NOT free-form CRUD (submit/cancel/amend, approval, posting)?

### Takeaway
Four distinct built-in lifecycle models exist and none is a generic state machine: Frappe's three-value docstatus with amend-as-new-document, Dataverse's two-level state/status-reason pair with optional transition enforcement, Salesforce's approval process that locks the record while pending, and SAP RAP's draft/active duality with Edit/Activate/Discard/Resume/Prepare. A user-defined workflow engine is layered on top of these (Frappe Workflow, Dataverse business process flows), not instead of them.

### Cited Findings
- **Frappe docstatus**: "The docstatus will always have one of the following three values": Draft (0), Submitted (1), Cancelled (2). "Documents that are not submittable will always remain in the "draft" state. Documents that are submittable can optionally proceed from the draft state to the "submitted", and then to the "cancelled" state." "Documents in the submitted and cancelled state cannot be edited", except that "for individual fields we can explicitly allow edits, even when the document is in the submitted state." "The docstatus gets stored as an integer value in each Doctype table of the database." [F] — [Frappe: Docstatus](https://docs.frappe.io/framework/doctypes/docstatus)
- **Frappe amend**: a cancelled document can be amended; the new document links back through the Amended From field. [F] — [Frappe tutorial: Types of DocType](https://docs.frappe.io/framework/user/en/tutorial/types-of-doctype.md). "Amended documents have a suffix (`-1`, `-2` etc) to the original document". [F] — [Frappe: Naming](https://docs.frappe.io/framework/user/en/basics/doctypes/naming)
- **Frappe lifecycle hooks**: `before_submit`, `on_submit`, `before_cancel`, `on_cancel`, `before_update_after_submit`, `on_update_after_submit`. [F] — [Frappe: Controllers](https://docs.frappe.io/framework/user/en/basics/doctypes/controllers)
- **Frappe Workflow**: each workflow state has a Doc Status ("Saved = 0, Submitted = 1, Cancelled = 2") and can update a field; transitions can carry a condition such as `doc.grand_total <= 100000`; Is Active — "On ticking this, all other Workflows for the selected DocType become inactive."; a workflow replaces the standard Save/Submit flow; email alerts notify users of "next possible workflow actions". [F] — [ERPNext: Workflows](https://docs.frappe.io/erpnext/user/manual/en/workflows)
- **Frappe audit caveat**: change tracking is hard for submittable documents that are cancelled and amended because the document name changes. [S] — [Frappe: Audit trail](https://docs.frappe.io/framework/user/en/audit-trail)
- **Odoo**: no document-lifecycle kind; `state` is a reserved field name for "lifecycle stages of the object", and `active` toggles "the global visibility of the record" (archiving). [F] — [Odoo 19 ORM API](https://www.odoo.com/documentation/19.0/developer/reference/backend/orm.html)
- **Dataverse state model**: `statecode` (Status) — "Represents the state of the record. For custom tables this value is Active or Inactive. You can't add more state choices but you can change the choice labels."; `statuscode` (Status Reason) — "Represents a status that is linked to a specific state. Each state must have at least one possible status. You can add more status choices". Custom transitions: when `EnforceStateTransitions` is true, a record "can only be changed to one of the allowed `statuscode` values"; state changes go through a dedicated `SetStateRequest` message rather than a plain update. [F] — [Microsoft Learn: Define custom state model transitions](https://learn.microsoft.com/en-us/power-apps/developer/data-platform/define-custom-state-model-transitions)
- Dataverse example of a non-default state set: PhoneCall has Open / Completed / Canceled with status reasons Made, Received, Canceled. "You can't customize the set of valid state codes for a table, but you can customize the status codes." [F] — [Microsoft Learn: Work with table definitions](https://learn.microsoft.com/en-us/power-apps/developer/data-platform/entity-metadata)
- Dataverse cascade interacts with state: "Cascade Active" applies an action only to child rows whose state code is Active. [F] — [Microsoft Learn: Configure table relationship cascading behavior](https://learn.microsoft.com/en-us/power-apps/developer/data-platform/configure-entity-relationship-cascading-behavior)
- **Dataverse business process flow**: "A business process flow consists of stages and steps. A stage is linked to a Dataverse table, and steps are typically linked to columns in the table for the stage."; "a process can span a maximum of five unique tables"; maximum 30 stages per process and 30 steps per stage; each business process flow creates its own Dataverse table that tracks process instances and their current stage. [S] — [Microsoft Learn: Create a business process flow](https://learn.microsoft.com/power-automate/create-business-process-flow); [Microsoft Learn training: Business process flows](https://learn.microsoft.com/en-au/training/modules/power-automate-architecture/6-business-process-flows)
- **Salesforce approval process**: "An initial submission action occurs when a user first submits a record for approval. (By default, the record is locked.)"; submission actions can be email alert, field update, task, outbound message, flow; "Final approval actions occur only when a record is approved and there are no further approval steps."; final rejection actions run on rejection. [S] — [Trailhead: Approvals (Business Process Automation)](https://trailhead.salesforce.com/content/learn/modules/business_process_automation/approvals). "Salesforce admins can edit locked records." [S] — [Apex Reference: Approval class](https://developer.salesforce.com/docs/atlas.en-us.apexref.meta/apexref/apex_methods_system_approval.htm)
- **SAP RAP draft**: "These persistent temporary versions are known as Drafts"; "Drafts are not stored in the same database tables as the active versions"; "Draft business objects need two separate database tables for each entity"; enabled with "the statement with draft;". Draft actions: "The draft action EDIT copies an active instance to a draft instance"; "The draft action ACTIVATE is the inverse action to EDIT."; "The draft action DISCARD deletes the draft instance and removes the related data"; "The draft action RESUME is executed when a user continues to work on a draft instance"; "The draft action PREPARE is a determine action."; "ACTIVATE includes an implicit execution of PREPARE."; "In draft-enabled RAP BOs, it is mandatory to define a total ETag field."; "When a draft instance is created for an existing active instance, the active instance receives an exclusive lock."; "The exclusive lock is not bound to the ABAP session."; "By default, the maximum lifetime for an exclusive lock is set to 15 minutes." [F] — [SAP Learning: Understanding the Draft Concept](https://learning.sap.com/courses/building-transactional-apps-with-the-abap-restful-application-programming-model/understanding-the-draft-concept)
- **SAP RAP save-time rules**: determinations and validations `ON SAVE` run in the `finalize` / `check_before_save` steps of the save sequence; the draft indicator `%is_draft` "indicates whether a RAP BO instance is active or not". [F] — [SAP-samples ABAP cheat sheets](https://github.com/SAP-samples/abap-cheat-sheets/blob/main/08_EML_ABAP_for_RAP.md)
- **Salesforce platform events** are a publish-only lifecycle: inserted like sObjects, not queryable, retained 72 hours, optionally published only after commit. [F] — [Trailhead: Define and Publish Platform Events](https://trailhead.salesforce.com/content/learn/modules/platform_events_basics/platform_events_define_publish)

### Inferences
- "Submittable document" is not the same as our `Workflow` archetype. Its defining properties are: a fixed three-state backbone, whole-record immutability after submit with a per-field allow-list, cancel as a reversing transition (never delete), and amend = create a new record that references the cancelled one and derives its number from it. Frappe's Workflow maps user-defined states onto this backbone rather than replacing it. Our catalog would need either a `Document`/`Submittable` archetype or the combination Workflow + "immutable after state X" + "amend" trait; neither exists today.
- A two-level status (coarse system state driving platform behaviour + fine user-defined reason) appears in Frappe (docstatus + workflow state), Dataverse (statecode + statuscode) and RAP (draft/active + business status). This suggests `Workflow` should separate a small fixed set of state *categories* (e.g. open / final-positive / final-negative) from user-named states, so other features (cascade "active only", immutability, filtering) can key off the category.
- RAP draft is a different concept from a "Draft" workflow state: it is a server-side, per-user, persisted edit session of an existing active record (plus new-record drafts), with an exclusive lock on the active record and validations deferred to Prepare/Activate. No item in our catalog covers it; the nearest are `Versioned` (optimistic only) and `Revisioned` (history, not pending edits).
- Record locking as a lifecycle effect (Salesforce approval lock, Frappe submitted, RAP draft exclusive lock) recurs on 3 platforms. We have only optimistic concurrency (`Versioned`).
- "Activate/deactivate" (Dataverse statecode Active/Inactive on every custom table; Odoo `active`) is a universal mini-lifecycle distinct from soft delete: inactive records stay referenced and visible in history but are hidden from pickers and skipped by "active only" cascades. Our `SoftDeletable` models deletion, not archival.
- Approval is modelled as a separate overlay object (process definition + steps + approvers + lock + recall), not as states hard-coded in the entity. For our catalog this argues for an `Approval` trait (or Workflow preset) rather than leaving it to hand-written `Workflow` transitions.
- State change as a dedicated message (Dataverse `SetState`, Frappe `submit()`/`cancel()`, RAP actions) rather than a PATCH of the status field is the norm; this is consistent with our `Action`/`Workflow` transition endpoints.

### Gaps
- No readable official source was found for Odoo document flows (e.g. `sale.order` draft/sent/sale/cancel) as a framework feature; in Odoo they are per-model conventions built on the `state` field, which is why only the reserved-field sentence is cited.
- Salesforce approval recall behaviour and step/approver configuration were only seen in a third-party study guide; not cited as fact.
- "Posting" in the accounting sense (ERPNext GL entries on submit, SAP document posting) was not researched at the application level; the framework-level mechanism is the submit hook (Frappe) or an action plus save-sequence logic (RAP).
- Dataverse BPF facts are from search snippets, not a full page read.

## How are hierarchies/trees, polymorphic references ("attach to any record"), document numbering sequences, and transient/wizard records modeled?

### Takeaway
Trees, polymorphic references and number sequences are first-class on at least four of the five platforms each, with dedicated storage conventions (nested set / materialised path; type+id pair; sequence objects with prefix, padding, period and gap-free variants). Transient/wizard records are specific to Odoo, with TTL storage (Dataverse elastic tables) and retained event buses (Salesforce) as the nearest relatives.

- Frappe Virtual DocType, Salesforce external objects (Salesforce Connect), Dataverse virtual tables ("contain data that is sourced from an external database dynamically at runtime"), RAP unmanaged implementation — see the kind findings in the first section. [F] — [Microsoft Learn: Types of tables](https://learn.microsoft.com/en-us/power-apps/maker/data-platform/types-of-entities)

### Inferences
- Numbering has four independent design axes that all platforms expose and that a `Numbered`/`Sequence` trait would need: (1) pattern (prefix, padding, date parts, field interpolation, random part); (2) scope/partition of the counter (per series, per company/tenant, per date range/fiscal period, per rule condition); (3) gap policy (fast with gaps vs gap-free with a lock); (4) assignment time (at create/draft vs at save/submit — RAP early vs late; Frappe draft names vs amended suffix). Our catalog has no numbering concept at all; this is the single clearest gap because all five platforms have it.
- Polymorphic references come in three strengths: plain "any record" pointer (Frappe Dynamic Link, Odoo Reference), constrained union of target types (Salesforce Who/What, Dataverse Customer/multi-table), and owning polymorphic parent (Dataverse Regarding with cascade). Cross-cutting features such as attachments, comments, activities and tags are all implemented on top of this primitive, so a single `AttachableTo<any>` / polymorphic `Under` primitive would unlock several traits.
- Trees need more than a nullable self-reference: the platforms add a materialised structure (nested set `lft/rgt` or `parent_path`) for subtree queries, a leaf/group flag, and subtree-aware permissions (Frappe descendants). A `Tree` trait should generate ancestors/descendants endpoints and cycle checks.
- Odoo's transient model is essentially "an Action's input form persisted for a short time" (wizard). In an HTTP API framework the equivalent is an `Action` request DTO, optionally with `Expiring`; it is probably not a missing archetype for us, only a naming difference. The genuinely missing temporary concept is RAP-style draft.

- Dataverse self-referential hierarchical relationships, hierarchy security and rollup-over-hierarchy were not verified with a fetched page.
- Salesforce auto-number field format and self-lookup hierarchies (e.g. Account parent) were not verified.
- SAP CDS hierarchies (tree views over self-associations) and RAP treeviews were not researched.
- The Frappe tree API page (docs.frappe.io/framework/user/en/api/tree) was found by search but not fetched; `parent_<doctype>` and `old_parent` columns are unverified.

## Which concepts recur across 3+ platforms (strong signal they are fundamental) vs. are platform-specific?
